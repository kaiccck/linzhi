## 0. 一页摘要

**问题。** 15 分钟生活圈的常见评估方式是以社区为圆心画一个 1 km 的圆，再数圆里有几家设施。但居民走的是路网：河道、高架、封闭大院都会让直线 760 m 的社区卫生服务中心变成 1.4 km 的步行路程。赛题要求基于真实路网计算步行等时圈、统计设施覆盖、找出服务盲区，并且鼓励"不拿底层路网数据，只靠地图 API 测时推导可达范围"。

**我们在张江的实测（四个片区，百度批量算路，小区名单逐条对照官方资料核实）：**

| 发现                         | 数据                                                                                                                                      |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 直线 15 分钟圆把可达面积高估 | 申城佳苑 **1.88 倍**（1.86 km² 对 3.48 km²）、玉兰香苑 2.12 倍、万科翡翠公园 1.66 倍、决赛场地（海科路 1650 号）周边 **3.03 倍**          |
| 15 分钟实际有效半径（中位）  | **约 730–775 m**，而不是 1,053 m                                                                                                          |
| 逐小区 × 五类设施的服务缺口  | 玉兰香苑 14 个小区：直线 1 km 只找到 **7 个**缺口，实测步行核实 **16 个**；AI 小镇周边 7 → 12；申城佳苑 0 → 3                             |
| 体检评分（实测 / 直线）      | 玉兰香苑 **77 / 90**（社区卫生覆盖率 29% / 71%）、AI 小镇 66 / 80、万科翡翠公园 60 / 60（1 km 内没有菜市场与社区卫生）、申城佳苑 94 / 100 |

数据本身也要核实。百度"住宅区"检索会把居委会办公点、工业园大门、写字楼、已动迁的村宅、同一小区的楼栋当成小区——玉兰香苑片区 28 个检索结果里只有 14 个是独立的住宅小区，不核实就会凭空多出 24 个缺口；设施侧，百度把浦东新区商务委认定的标准化菜市场标成"购物""生鲜超市"，把店名带"（孙桥菜场店）"的饭店当成菜场摊位。邻至对照官方名录与人工核实清单逐条处理（§6.4、§7.1）。

**我们的方案。** 一个微信小程序（主应用）加 Web 工作台、REST/SSE 服务和一套可复用的 TypeScript 算法库，只调用百度 Web 服务 API：

1. **按配额设计的等时圈引擎**：插值"绕行系数 ρ"而不是时间（去趋势插值），用 API 测时之间的 Lipschitz 矛盾自动发现河道和高架，并主动加密边界带采样。240 条路线下与 796 点稠密实测参照的 15 分钟区域 IoU 为 0.916（直线圆 0.516），与百度官方等距圈逐小区判定一致率 95%（§5.9）。
2. **逐小区五类设施判定**：幼儿园、小学、菜市场、药店、社区卫生，步行 1 km：走得到、绕路太远（伪覆盖）、直线也远（盲区）、临界；小学按官方**对口学校**而不是最近学校；未核实的如实标为待核实，商办产权小区标"无对口小学"。
3. **体检评分**：五类覆盖率的平均，带标准、算法、分档刻度尺和"按直线距离算"的对照分。
4. **规划助手**：沿实测路线的候选点做最大覆盖选址并实测核验；用户放置虚拟设施，立即给出能补上哪些小区、评分从多少变成多少，再一键实测核验。
5. **AI 层**：体检顾问 Agent，数字只来自工具调用并逐个校验；同时提供 MCP Server。
6. **工程**：按接口区分鉴权、自适应限流、持久缓存与配额账本、分级降级、样例模式。评委不配置 Key 也能一键跑通演示。

### 1.3 判定口径

按赛题口径判定：五类设施都以**步行 1,000 m**为界。v0.1 曾计划并列国标口径（GB 50180-2018：小学、菜市场 500 m，药店、幼儿园 300 m），实现中发现五类设施在国标中分属不同层级的生活圈、距离各不相同，并列两套结论反而让人看不懂，所以只保留赛题口径。

生鲜超市不计入菜市场（赛题严格口径），官方名录认定的标准化菜市场除外（浦商生鲜等以"生鲜"命名的标准化菜市场按名录改类）。对菜市场缺口的小区，另行列出判定距离内步行能到的能买菜的店（"买菜替代"），只作提示，不改变判定。

### 2.3 官方等时圈接口

百度的等时圈（`/logistics_truck/v1/isochrone`）和等距圈（`/isodistance`）属于需工单开通的高级服务，每次只返回一个中心点、一个时长或距离的单个多边形：没有耗时场，不做设施覆盖和盲区分析，评委也无法用普通 Key 复现。本项目不把它放进核心链路，而是在开通后（2026-09-30 起）把它作为**独立对照**：

- 1 km 等距圈（从设施出入口步行）与本项目逐小区判定对照（2026-10-02，按当时的样例）：四个片区 310 项中 295 项一致（95.2%），不一致的 15 项都在多边形边缘 10–186 m 内。
- 15 分钟等时圈：官方按约 1.40 m/s 步行（比批量算路的 1.17 m/s 快），900 秒时面积偏大 1.45–1.63 倍；按速度折算到 752 秒后与稠密参照的 IoU 为 0.871 / 0.746（A / V），本项目为 0.916 / 0.861。

原始结果见 `research/api-probe/08_official_isochrone.md`、`09_official_isodistance.md`。

## 3. 总体架构

### 3.1 设计原则

1. **配额优先**：每个算法都以"每次体检消耗多少条路线"作为一等指标。
2. **诚实的数据**：每个数字都带来源标记（实测 / 缓存 / 估算 / 样例），估算区域在图上明确标出。
3. **算法与 I/O 分离**：核心算法是纯函数，可单测、可复现、可被 MCP 和 CLI 复用。
4. **离线可复现**：内置张江样例数据，评委不配置 Key 也能看到完整功能。
5. **一种语言**：前后端和工具链全部使用 TypeScript。

### 3.2 模块划分（pnpm monorepo）

```
.
├── packages/
│   ├── core/        # 纯算法：坐标、几何、等时圈、插值、等值线、POI 清洗、对口小学、盲区、选址（无 I/O，浏览器/小程序/Node 通用）
│   ├── baidu/       # 百度 Web 服务客户端：鉴权、调度、缓存、账本、降级、坐标转换
│   ├── engine/      # 实时体检流水线：把 core 与 baidu 串起来，逐阶段推送
│   ├── agent/       # AI 体检顾问：工具注册表、数字溯源校验、OpenAI 兼容客户端、报告生成
│   ├── mcp/         # MCP Server（stdio + Streamable HTTP）
│   └── eval/        # 精度–配额评测
├── apps/
│   ├── server/      # Fastify：REST + SSE 流式体检、样例、历史与分支、路线证据、问询；scripts/ 为样例数据脚本
│   ├── miniapp/     # 微信小程序（Taro 4 + React 18）：主应用
│   └── web/         # Web 工作台（React + Vite + 百度 JSAPI GL）
├── data/official/   # 官方名录：菜市场、小学、招生地段、社区卫生、排除清单、小区核实清单
├── data/samples/    # 张江四个样例片区与步行路线证据
└── research/        # 调研脚本与原始数据（不进入产品构建）
```

### 3.3 一次体检的数据流（SSE 逐阶段推送）

```
输入（地址 / 点选 / 坐标）
  → [定位] 地理编码 + 校验 + 逆地理（街道信息）                          约 1–3 次
  → [设施] 地点检索 $ 并集 + 分页 → 清洗 → 出入口                       3–6 次检索
  → [等时圈 A] 极坐标粗采样 48 点                  → 推送：粗等时圈        48 条路线
  → [等时圈 B] 路径前缀采集 4–6 条                 → 推送：路网骨架       4–6 次步行路线
  → [等时圈 C] 边界带加密 ×（2–4 轮）               → 推送：精修等时圈     96–192 条路线
  → [设施可达] 中心 → 设施 O×D                     → 推送：设施耗时       ≤ 100 条路线
  → [小区] 地点检索"住宅区" → 去重合并 → 剔除居委会与核实清单中的非住宅 → 官方名称   2–3 次检索
  → [盲区] 小区出入口 × 候选设施 O×D，直线剪枝 + 早停 → 推送：逐小区判定    ≤ 650 条路线
  → [对口] 招生地段匹配对口学校 → 小区 → 对口校门 O×D                       ≤ 40 条路线
  → [规划] 沿步行路线的候选点最大覆盖选址，前列实测核验 → 推送：规划建议   ≤ 100 条路线
  → [报告] 评分、灰色区域、圈内设施统计、AI 解读    → 推送：体检报告
```

## 4. API 调用策略（packages/baidu）

### 4.1 鉴权：按接口配置

| 配置项                                | 说明                                                                    |
| ------------------------------------- | ----------------------------------------------------------------------- |
| `BAIDU_BROWSER_AK`                    | 浏览器端，只开 JSAPI，配置 Referer 白名单                               |
| `BAIDU_SERVER_AK` + `BAIDU_SERVER_SK` | 服务端，SN 签名，用于地理编码、逆地理编码、坐标转换、地点检索、步行路线 |
| `BAIDU_MATRIX_AK`                     | 服务端，IP 白名单，只开批量算路（规避 §2.2 的 SN 问题）                 |
| `BAIDU_SERVER_AUTH=sn\|ip`            | 评委的 Key 可能是任一模式，两种都支持                                   |

SN 算法：`sn = md5(urlencode(path + "?" + query + SK))`。参数顺序必须与实际发送顺序一致，GET 请求中 `sn` 放在最后，步行路线接口需要附带 `timestamp`。实现已通过官方测试向量 `7de5a222…f9a0` 校验。SK 只存在于服务端，永不下发到浏览器。

### 4.2 调度与状态码策略

每个服务一个令牌桶，个人档 2 次/秒，企业档 20 次/秒。批量算路另设路线预算桶。并发默认为 1，采用 AIMD 自适应：连续成功时并发 +1（上限 3），遇到 401 时减半。

| status                                                  | 含义                   | 策略                                                                           |
| ------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------ |
| 0                                                       | 成功                   | 写缓存；`value==0` 的条目标记为缺失                                            |
| 1                                                       | 服务内部错误           | 退避重试 2 次                                                                  |
| 2                                                       | 参数错误               | 不重试，记录并报错（客户端缺陷）                                               |
| 3 / 4 / 5 / 9 / 101 / 102 / 200 / 210 / 211 / 220 / 240 | 鉴权、权限、配置类错误 | 不重试；界面提示具体原因和修复方法（例如"211：SN 校验失败，请检查 SK"）        |
| 302                                                     | 天配额超限             | 当日熔断该服务，切换到缓存或样例，界面显示"配额已用尽"                         |
| 401 / 402                                               | 并发超限               | 原批次指数退避（1、2、4、8、16 秒，加抖动）后重试，最多 5 次；实测缩小批量无效 |
| 网络或 TLS 错误                                         | 请求未到达百度         | 重试，不计入配额                                                               |

### 4.3 缓存与请求合并

- **两级缓存**：内存 LRU 加 SQLite（优先使用 Node 24 内置的 `node:sqlite`）。
- **缓存键**：服务名 + 规范化参数（坐标四舍五入到 1e-5 度，约 1 m；参数排序）。
- **有效期**：路线 30 天（实测步行耗时与路况无关）；POI 7 天；地理编码 30 天。
- **合并与去重**：相同 OD 对在同一批次内去重，并发的相同请求合并为一次（singleflight）。

### 4.4 配额账本与单次体检预算

每次体检开始前按档位预留预算（`packages/engine/src/budget.ts`），各阶段只能在自己的额度内消费，不足时按"生活服务 → 买菜替代 → 必查类别"的顺序先放弃次要部分：

| 阶段           | 接口                           | 个人档            | 企业档            |
| -------------- | ------------------------------ | ----------------- | ----------------- |
| 定位           | 地理编码、地点检索、逆地理编码 | ≤ 3               | ≤ 3               |
| 设施与小区检索 | 地点检索（含民生、生活服务类） | ≤ 20 页           | ≤ 25 页           |
| 等时圈         | 批量算路 + 轻量步行路线        | 48 + 192 条，4 次 | 48 + 288 条，6 次 |
| 盲区           | 批量算路                       | ≤ 650 条          | ≤ 1,500 条        |
| 对口小学       | 批量算路                       | ≤ 40 条           | ≤ 80 条           |
| 规划核验       | 批量算路                       | ≤ 100 条          | ≤ 200 条          |
| 小区上限       | —                              | 30 个             | 60 个             |

实测：玉兰香苑片区企业档冷启动一次用地点检索 11 次、批量算路约 224 条（部分命中缓存）。缓存命中的体检不消耗配额；`/api/health` 实时显示各接口当日余量，达到 90% 时拒绝新的冷启动分析。

### 4.5 降级链

| 对象         | 降级顺序（界面标记）                                                                        |
| ------------ | ------------------------------------------------------------------------------------------- |

### 4.6 地理编码校验

1. 调用地理编码；若 `precise=0` 或 `comprehension < 80`，进入校验。

## 5. 等时圈生成算法（packages/core/isochrone）

### 5.1 形式化与两个关键事实

- 记中心为 c，任意点为 x，直线距离 r(x) = |x − c|，百度步行路线距离 L(x)，步行耗时 t(x) = L(x) / v。实测 v = 1.17 m/s，为常数。
- **事实 1（下界）**：L(x) ≥ r(x)，所以 t(x) ≥ r(x)/v。15 分钟可达区域一定落在半径 vT = 1,053 m 的圆内，圆外不用采样。
- **事实 2（绕行系数）**：定义 ρ(x) = L(x) / r(x) ≥ 1。张江三个社区实测 ρ 的中位数为 1.34–1.46，90 分位为 1.78–2.36。

### 5.2 去趋势插值：插值 ρ，而不是 t

直接对 t 做反距离加权（IDW）会产生系统偏差：t 随 r 近似线性增长，而 IDW 是局部加权平均，边界附近的估计值会被内侧样本拉低，等时圈因此系统性偏大。

我们以直线距离作为已知的漂移项：先插值 ρ，再令 t̂(x) = max(ρ̂(x), 1) · r(x) / v。

- 自动满足事实 1 的下界。
- ρ 在无量纲尺度（约 1–2.5）上变化，比 t 更平稳，插值误差更小。
- 初步验证（申城佳苑 432 个批量算路样本，留一法交叉验证）：插值 ρ 的平均绝对误差为 54.4 秒、90 分位误差为 125.3 秒；直接插值时间则为 57.2 秒、145.3 秒。90 分位误差降低 14%。实现见 `design/mockups/data-build/field.ts`。
- 各向异性权重：w_i = 1 / ( max(d_i, 15 m)² · (1 + α·Δθ_i) )，其中 Δθ_i 是样本与待估点相对中心的方位角差，α = 1。同一方向上的样本更可信。
- 近邻数 k = 10，且只使用"可见"样本：连线不穿过已检出的断裂（§5.3）。

### 5.3 Lipschitz 断裂检测：只用 API 测时发现河道和高架

对任意两点 x₁、x₂，由三角不等式，|t(x₁) − t(x₂)| ≤ L(x₁, x₂)/v，其中 L(x₁, x₂) 是两点之间的路网距离。

定义样本对的断裂强度 κ₁₂ = |t₁ − t₂| · v / |x₁ − x₂|。若 κ₁₂ > κ*（默认 2.5），则两点间的路网距离至少是直线距离的 κ* 倍。这是可以证明的结论，不是经验猜测：两点之间必有阻隔（河道、无路口的高架、铁路、封闭大院）。

实现步骤：

1. 对样本做 Delaunay 三角剖分，逐边计算 κ。
2. κ > κ* 的边，在其中垂线附近记为断裂段。
3. 插值时，连线穿过断裂段的样本不参与（§5.2 中的"可见"约束）。
4. 断裂附近提高采样优先级（§5.4）。

全过程不使用任何底层路网数据，正好对应赛题 30% 档第 3 项的要求。

两条防误判规则：

- 一条边还必须意味着至少 20 m 的额外步行，才算断裂。否则相距 0.45 m、耗时差 2 秒的两个点，会因为绑路噪声算出 κ = 5.2。
- 长度超过 400 m 的边不参与判断，因为它们无法定位阻隔的位置。

实测效果：在申城佳苑的 2,013 条三角边中检出 268 段断裂。开启可见性约束后，插值留一误差从平均 54.4 秒、90 分位 125.3 秒，降到平均 50.0 秒、90 分位 121.3 秒；每个目标点都在剔除自身后重新检测断裂，比较是公平的。

### 5.4 主动采样：三阶段

| 阶段           | 做法                                                                                                                                                                         | 消耗                         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| A 极坐标粗采样 | 16 个方位 × 3 个半径（0.33R、0.67R、1.0R，其中 R = vT），1 次批量请求                                                                                                        | 48 条路线                    |
| B 路径前缀采集 | 选 ρ 最大或方位跳变最大的 4–6 个方向，向 1.25R 处请求轻量步行路线（`steps_info=1`）。每段的耗时按长度分摊到路径点上，每条路线约得到 30 个带时间的路网点（实测点距约 15 m）   | 4–6 次步行路线（独立配额池） |
| C 边界带加密   | 候选为 40 m 格点。评分 s(x) = exp(−(t̂−T)² / 2σ²) · (1 + β·断裂邻近度)，σ 由邻域 ρ 的加权标准差和最近样本距离估计。每轮选 48 个点（泊松盘最小间距 60 m），1 次请求；最多 4 轮 | 48–192 条路线                |

停止条件：本轮前后 15 分钟区域的对称差面积小于 3%，或预算用尽。

合计约 100–240 条路线加 4–6 次步行路线，同时得到 5、10、15 分钟三档结果。

### 5.5 等值面提取

- 在 25 m 栅格上计算 t̂，用 marching squares 提取 300、600、900 秒等值带。
- 用 Chaikin 平滑 2 次，再用 Douglas-Peucker 简化（容差 5 m）。
- 输出 GeoJSON MultiPolygon，保留孔洞。与竞品不同，结果不强制为"星形"，能表达"桥那头能到、河这边反而到不了"。

### 5.6 不确定性表达

- 标出 |t̂ − T| < 1.64σ 的格子作为"边界不确定带"，在图上用半透明描边显示。
- 样本点区分"实测"与"路径采集"。
- 报告给出等时圈面积的估计区间。

### 5.7 人群画像

| 画像         | 速度                              | 说明                                                                            |
| ------------ | --------------------------------- | ------------------------------------------------------------------------------- |
| 成人（默认） | 百度原始耗时                      | 1.17 m/s                                                                        |
| 老年人       | t = L / 0.9 m/s（可配置）         | 参考：美国 MUTCD 对慢速行人（老人等）建议 3.0 ft/s ≈ 0.91 m/s；后续对齐国内规范 |

### 5.8 过街等待修正（实验）

批量算路的耗时就是 距离 / 1.17 m/s，看不出任何等待；轻量步行路线慢 3.5–6.6%，但百度未说明原因。赛题痛点又点名了红绿灯，所以我们自建一层可标定的修正。做法如下：

1. 从轻量步行路线的分段说明（"过马路"、人行横道、天桥、地下通道）中识别过街节点。
2. 每个节点叠加等待时间（信号灯默认 30 秒，可配置）。
3. 用实地步行计时（§11.2）标定参数。

在图上以"含等待"和"不含等待"两条等时线对比展示。

### 6.2 检索策略

- **范围**：检索范围 = 分析范围 + 1 km 缓冲。竞品只检索中心 1.8 km 内的设施，却判断 1.5 km 外网格点的 1 km 覆盖，边缘会产生假盲区。
- **参数**：地点检索 v3 `around`，`radius_limit=true`，`scope=2`，`page_size=20`。当 `page_num·20 < total` 时继续翻页。
- **截断处理**：单次检索 total 上限为 150。命中上限时，按关键词拆分，或把区域四叉切分后递归检索。
- **配额**：一次社区体检约需 3–6 次检索，同一片区的多个中心点共享检索结果。

### 6.3 清洗流水线

1. **标签过滤**：按 `classified_poi_tag` 白名单过滤。
2. **名称黑名单**：小学排除"培训、辅导、托管、兴趣、英语"；药店排除"兽药、宠物、医疗器械"。
3. **摊位归并**：名称形如"（孙桥菜市场店）"，或标签为 购物;肉店、水产等、且位于某菜市场 60 m 内的 POI，归并为该菜市场实体，不单独计数。张江实测中的"英英肉店(孙桥菜市场店)"就属于这种情况。标签为"美食"的店先按餐饮归类，即使店名带"（孙桥菜场店）"也不算摊位（仙味楼上海本帮菜江浙菜(孙桥菜场店) 曾被误当成菜场，已纠正）。
4. **排除清单**：按 uid 或名称规则剔除经核实不是设施的点，例如叮咚买菜、美团买菜（小象超市）、每日优鲜的前置仓（线上下单、配送到家，不是可以走去买菜的地方），2026 年不招生的校区（`data/official/exclusions.json`，每条带理由、来源与日期）。
5. **生鲜超市单独标注**：不计入菜市场；菜市场缺口的小区另列"买菜替代"（见 §1.3）。
6. **去重**：依次按 uid、`parent_id`、名称归一化 + 30 m 内去重。
7. **算路终点**：取 `navi_location`（出入口），缺失时退回 POI 坐标。
8. **置信度与溯源**：每个 POI 记录来源、标签匹配度和是否人工核实。

| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 百度地点检索          | 主数据源                                                                                                                                                                                                                                                                                                                                                                         |
| OpenStreetMap（ODbL） | 交叉校验，发现百度缺失的设施。坐标用百度坐标转换 API 从 WGS84 转为 BD-09（对应评分项"坐标转换"），并与本地公式互校（实测往返误差 0.66 m）                                                                                                                                                                                                                                        |
| 政府公开名录          | 已接入（`data/official/`），与百度 POI 融合（确认 / 改类 / 补充）：浦东新区商务委 2023Q4 标准化菜市场名录（196 家）、浦东新区教育局 2026 年小学招生名单（267 个校区）、市卫健委社区卫生服务中心（浦东 46 家）；另有浦东新区教育局《2026 年浦东新区小学招生地段公示》（全区 6,993 行，张江镇 234 行转录，用于对口小学）、人工核实的设施排除清单与小区核实清单（每条带来源与日期） |
| 实地标注              | 样例社区约 150 个 POI 的人工核实结果，作为清洗效果的真值                                                                                                                                                                                                                                                                                                                         |

**官方名录融合（已实现，`packages/engine/src/official.ts`）。** 名录条目按地址用百度地理编码补坐标（记录精度），体检时取设施检索半径内状态为"正常参评"的条目，与百度检索结果（含被标签过滤掉的"购物"等 POI）匹配：分店名去掉品牌与业态词后相同（如"浦商生鲜(申城佳苑店)"与"浦商生鲜申城佳苑店"都归为"申城佳苑"），或门牌地址相同，且相距不超过 250 m（两者都一致时放宽到 400 m）。匹配上则按名录改正类别并保留百度的 uid 和出入口；匹配不上则按官方地址补入（`source: 'gov'`）；装修改造、业态调整的条目不计。每次体检在 `meta.notes` 中写明确认、改类、补充各几家。

张江实例：浦商生鲜(申城佳苑店) 在百度中只标为"购物"，浦商生鲜(环西店)、浦商农产品(紫薇店) 标为"生鲜超市"，按关键词和赛题严格口径都会被漏掉。同一批小区、同一批路线，融合前后对比（2026-09-28，实时引擎的同一中心点）：申城佳苑片区的菜市场缺口从 11 个降到 5 个，玉兰香苑片区从 13 个降到 10 个。

### 6.5 清洗质量评估

- 按类别报告清洗前后的精确率和召回率（对照实地标注集）。
- 例如百度百科记载的"申城佳苑菜场"在百度 POI 中缺失，属于召回问题，需要实地核实后记录。
- 可选：用 LLM 对歧义名称做二次判定（§8.4），并用同一标注集评估其准确率。

## 7. 服务盲区识别与规划建议（packages/core/coverage）

### 7.1 需求点：小区识别与核实

需求点是住宅小区的出入口：地点检索"住宅区$小区"，以 `navi_location`（导航入口）为出发点，没有时取门 POI 或小区点位。百度对一个大型小区会分别列出母点、各期、楼栋、大门和别名，所以先合并：去掉门与楼栋后缀按名称合并；期数写法统一（I 期 = 1 期 = 一期）；同一 `parent_id` 的子点并入母点；地址写明另一小区且相距 30 m 内的点视为别名（`packages/engine/src/residential.ts`，每次合并写入 `stats.residential_dedupe`）。

合并后仍有不是住宅的点。2026-10 我们对四个样例片区的每个点逐条核实（张江镇人民政府《住宅小区非生活垃圾规范化清运招标文件》所附住宅小区清单 104 个小区、浦东新区教育局 2026 年招生地段全区 6,993 行、张江镇居村委地址一览表、公开资料），结论写进 `data/official/community-review.json`（每条含百度 uid、理由、来源、核实日期）：

| 类型           | 处理                         | 例子（玉兰香苑片区）                                                |
| -------------- | ---------------------------- | ------------------------------------------------------------------- |
| 居委会办公点   | 剔除（另有名称规则自动剔除） | 江夏社区、江丰社区、江衡社区、江苑社区、江益社区、江春社区          |
| 不是住宅       | 剔除                         | 益丰工业小区（百度类别为"出入口;门"）、梦想园（895 创新基地写字楼） |
| 同一小区的楼栋 | 剔除                         | 益丰路55弄109号、益江路55弄113号（均属春港丽园）                    |
| 位置标错       | 剔除                         | 华陇小区（官方在建中路461弄，百度点位在 4 km 外）                   |
| 查无此小区     | 剔除                         | 东窑新村、创新公寓、旺辰公寓                                        |
| 商办产权       | 保留，小学"无对口"           | 张江公馆（50 年产权商住公寓，全区招生地段中没有它）                 |
| 地址写法不同   | 保留，按官方写法匹配         | 日月光员工生活区（百度"银冬路568号"，招生地段"银东路568号"）        |
| 官方名称       | 保留，改名                   | 益江路511弄 → 玉兰香苑二期A块（招生地段登记名）                     |

名称规则：两个汉字加"社区 / 居委会 / 居民区"（如"江夏社区"）是上海居委会的叫法，从不是小区名，实时体检直接剔除。核实清单在实时体检中按 uid 生效：在玉兰香苑以企业档重新体检，引擎自动去掉 6 个居委会和 8 个核实过的非住宅点，留下的 14 个小区与人工核实结果完全一致。

### 7.2 判定

以阈值 D = 1,000 m（赛题口径），对每个小区 × 五类设施（幼儿园、小学、菜市场、药店、社区卫生）：

| 状态             | 条件               | 界面用语 | 含义                             |
| ---------------- | ------------------ | -------- | -------------------------------- |
| 覆盖             | 步行最近 L ≤ D     | 走得到   | 真的走得到                       |
| **伪覆盖**       | 直线最近 r ≤ D < L | 绕路太远 | 画圆以为有，实际要绕路           |
| 盲区             | r > D              | 直线也远 | 附近确实没有                     |
| 临界（附加标记） | \|L − D\| ≤ 50 m   | 临界     | 结论对终点选取敏感，需要实地核实 |
| 待核实（不计入） | 未对该小区单独算路 | 待核     | 不当作缺口，也不画结论颜色       |

任一类缺失，即为该小区的服务缺口。界面不用"伪覆盖""盲区"这样的术语，而用"绕路太远""直线也远"直接说出原因；AI 回答第一次出现时括注术语。

### 7.3 计算

1. 对每个小区、每个类别，把候选设施按直线距离排序，只保留 r ≤ D 的候选（步行距离 ≥ 直线距离）。
2. 若候选为空，直接判为盲区，不消耗配额（"直线就超过，下界已证明"）。
3. 否则以小区出入口为起点、候选为终点做 O×D 批量请求（每次 ≤ 50 对），按轮次推进：某小区一旦找到 L ≤ D 的设施就停止，不再查询它更远的候选。
4. 预算用尽时，未算到的判定标为待核实，并记录"还有更近的候选没有算路"。

### 7.4 对口小学

小学的可达性看**对口学校**而不是最近的学校：居民上不了隔壁那所。按浦东新区教育局《2026 年浦东新区小学招生地段公示》匹配：

1. 先按弄号（小区名或百度地址中的"××路××弄"），再按小区名、名称缺期或块、去掉期或块的基名匹配；同名条目对口不同学校时不判定。
2. 地段表写明校区时，算到该校区校门的步行路线；只写学校、而学校有多个校区时（如孙桥小学张江校区、申江校区），**不按距离推定校区**，标为"校区待核实"。
3. 商办产权小区（核实清单 `no_catchment`）没有对口学校，小学一项显示"无对口小学"：既不算缺口，也不算待核实。

### 7.5 灰色区域

- 把小区判定结果分配到 50 m 栅格（有小区轮廓时用 25 m 栅格并限定在轮廓及外扩 120 m 内，水面不计）。
- 按缺失类别数分级（缺 1、2、3、4 类），用 marching squares 生成"灰色区域"多边形；只按已核实的判定计数。
- 小程序只填充最外一级、内层描边，避免叠加变暗遮住小区编号。

### 7.6 体检评分

为了让第一次打开的人也能看懂"这个片区怎么样"，给出一个 0–100 的分数：

- **覆盖率**：某类设施，步行 1 km 内走得到的小区 ÷ 已核实的小区（待核实、无对口的不计）。
- **体检评分** = 五类覆盖率的平均 × 100；分档 ≥ 90 良好、≥ 75 基本达标、≥ 60 需关注、其余待改善。
- **按直线距离算的分数**：同样的设施和规则，只把步行距离换成直线距离——两个分数之差就是"画圆"高估的部分。

小程序把评分与标准（五类设施图标）、算法、分档刻度尺（实测与直线两个标记）放在一起，雷达图展示各类覆盖率；AI 顾问与 Markdown 报告给出同一个分数（`packages/agent` 与 `apps/miniapp` 的实现由同一组样例测试互相核对）。

### 7.7 规划建议

| 步骤       | 做法                                                                                                                                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 候选选址点 | 路径前缀采集得到的沿街点（每 50 m 取一个，天然位于可步行的街道上）                                                                                                                                             |
| 覆盖估计   | L̂(s, d) = max( max(ρ̂(s), ρ̂(d)) · r(s, d), \|t̂(s) − t̂(d)\| · v )。用 132 条实测的小区→设施路线检验 1 公里判定：这个公式判对 92.4%，误判为可达的 5 条；只用候选点处 ρ̂ 的简单公式只判对 85.6%，误判为可达的 15 条 |
| 选址       | 只为已核实的缺口选址；贪心最大覆盖（MCLP），每类最多 3 个；小学不做选址（对口学校由招生政策决定，新开一所不改变对口）                                                                                          |
| 核验       | 排名前列的候选点做 1 × \|D\| 批量请求，用实测距离重算；核验结果改变排名时重新贪心                                                                                                                              |
| 输出       | 例如"东北向步行路线约 900 m 处新增 1 处菜市场，补上张江公馆、日月光员工生活区"，并给出补上之后的**体检评分**与该类覆盖率（玉兰香苑：77 → 80，菜市场 86% → 100%）                                               |
| what-if    | 用户在地图上放置虚拟设施，前端先用 L̂ 即时估算并给出评分变化，再用 `POST /api/whatif` 实测核验：从该点到判定距离 × 1.5 内的每个小区做一次批量算路，结果保存为这次体检的一条核验记录（界面上的"核验过的位置"）   |

## 8. AI 能力（packages/agent、packages/mcp）

### 8.1 体检顾问 Agent

- 用户可以用自然语言提问，例如："评分是怎么来的？""老人买菜方便吗？""如果在张江公馆附近开一家菜市场呢？"
- 可用工具：定位、体检分析（可选画像）、查询盲区、模拟新增设施、对比社区、导出报告。
- **约束**：Agent 不自行计算任何数字，所有数字都来自工具返回值，并在回答中附上对应的工具结果编号；服务端逐个数字核对，不合规的回答退回模型修改。无法用工具回答时明确说明，不猜测。体检评分只能引用 `analyze_life_circle` 返回的 `score`（与小程序同一算法），不得自拟评级。
- 实测（DeepSeek，2026-10-13）：问"社区卫生为什么得分这么低？"，回答给出该类覆盖率与按直线算的覆盖率、绕路最严重的小区及其直线与步行距离，25 个数字全部通过溯源校验。
- 支持 OpenAI 兼容接口（文心、DeepSeek、通义等），通过 `LLM_BASE_URL`、`LLM_MODEL` 配置。未配置时退回模板化报告，功能不受影响。

### 8.2 MCP Server

对外暴露与 Agent 相同的工具：

- `locate_place`
- `analyze_life_circle`
- `get_isochrone`
- `list_service_gaps`
- `simulate_facility`
- `compare_sites`
- `export_report`

传输支持 stdio 和 Streamable HTTP。任何支持 MCP 的客户端（Claude、Cursor、Cherry Studio 等）都能直接给一个社区做体检。

与百度官方 MCP Server 的区别：官方提供的是地理编码、检索、算路等原子能力；我们提供的是"生活圈体检"这一更高层的分析能力，二者可以组合使用。

### 8.3 报告生成

报告包含结构化结论（体检评分与各类覆盖率、逐小区判定、灰色区域、圈内设施、规划建议）和方法说明。小程序内为可转发的报告页；`export_report` 导出 Markdown 与 GeoJSON。

### 8.4 LLM 辅助 POI 消歧（可选）

对名称歧义的 POI（例如"××学校"是否含小学部），由 LLM 在给定候选标签中选择。准确率在实地标注集上评估。未达到阈值的类别不启用此功能。

## 9. 可视化与交互（apps/miniapp，另有 apps/web）

### 9.1 设计原则

- **地图应用的结构**：以高德地图的结构（全屏地图 + 可拖动面板 + 地点卡片）和 Apple 地图的克制（留白、字重层级）为标准，不另造交互习惯。
- **先结论、后证据**：面板头部一句话结论（"12 个小区步行 1 公里内缺设施，按直线距离只看得出 4 个"），往下才是评分、范围、方法；单个小区页先给每类的步行距离，再给路线证据。
- **说人话**：界面用"走得到 / 绕路太远 / 直线也远 / 待核 / 无对口"，不用术语；评分旁边就写着标准和算法。
- **状态从不只靠颜色**：每个颜色旁边都有文字标签。

### 9.2 小程序结构

| 层级     | 内容                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 地图     | 百度坐标转为腾讯底图坐标；热力图、直线 15 分钟圈（虚线）、灰色区域、小区编号（按判定着色、自动避让）、所选类别的设施图标；路名与地名可见         |
| 面板头部 | 片区名、结论、规划补点 / 问 AI / 报告 / 转发、三个标签页                                                                                         |
| 概览     | 体检评分（标准、算法、刻度尺、雷达图）、15 分钟走得到的面积与时间轴（成人 / 老人）、灰色区域、绕路最远的方向（看路线）、怎么测出来的（看采样点） |
| 缺口小区 | 按类别切换，缺口在前，标明步行距离与原因；点进去是单个小区：五类设施的步行距离、实测步行路线与直线对比                                           |
| 周边设施 | 15 分钟走得到的 18 类设施，按医疗、教育、购物、养老、出行、生活服务、文体分组；点进去在地图上看每一处                                            |

| 其他页面 | 搜索（地址、小区、百度坐标、我的位置、最近体检、样例）、问 AI（推荐问题、引用卡片、小区链接回地图）、体检报告                                    |

### 9.3 等时圈热力图

耗时场在 25 m 栅格上按每分钟提取一条等值线，每层用很淡的沙色填充叠放：中心叠得最多、颜色最深，向外逐分钟变浅，形成连续的热力渐变；5、10 分钟画细线，当前时间（默认 15 分钟）画实线边界。拖动时间轴或点"走一遍"，范围从 0 分钟长到 15 分钟。小程序原生地图不绘制图片覆盖物（开发者工具模拟器中），所以全部用原生多边形实现，任何运行环境都能显示。Web 工作台用 Canvas 纹理绘制同一个耗时场。

### 9.4 Web 工作台

`apps/web` 是同一服务的桌面工作台（百度 JSAPI GL 底图、连续耗时色阶、逐小区核对表、路线证据、规划与问询），适合大屏讲解与核对数据；`docker compose up` 后在浏览器打开即可。

### 11.2 真值来源

1. 稠密参考网格（§5.9）。
2. 官方等时圈（若申请到试用）。
3. **实地步行计时**：在 A 选 10–15 条路线，含跨越高架、河道的路线；记录 GPS 轨迹和秒表时间，用于检验"百度耗时 vs 实走耗时"并标定过街等待。
4. **实地设施普查**：A 片区菜市场、药店、小学和其他类别约 150 个 POI，逐一确认是否存在、是否营业、出入口位置。

### 11.3 指标

- 等时圈：IoU、边界分类准确率、耗时误差、消耗的路线数。
- 盲区：逐小区判定与官方等距圈的一致率。
- POI：分类别的精确率和召回率。
- 性能：首屏时间、完整报告时间、缓存命中后的耗时。

### 11.4 结果

完整结果见《真实对比测试报告》。摘要（2026-10，样例小区经官方资料核实后）：

| 片区                   | 小区 | 15 分钟可达 / 直线圆 | 高估倍数 | 画圈缺口 → 实测缺口 | 体检评分（实测 / 直线） | 待核实             |
| ---------------------- | ---- | -------------------- | -------- | ------------------- | ----------------------- | ------------------ |
| A 申城佳苑             | 12   | 1.857 / 3.483 km²    | 1.88×    | 0 → 3               | 94 / 100                | 12（孙桥小学校区） |
| B 玉兰香苑（演示开场） | 14   | 1.645 / 3.483 km²    | 2.12×    | 7 → 16              | 77 / 90                 | 0                  |
| C 万科翡翠公园         | 7    | 2.096 / 3.483 km²    | 1.66×    | 14 → 14             | 60 / 60                 | 0                  |
| V AI 小镇服务中心周边  | 7    | 1.151 / 3.483 km²    | 3.03×    | 7 → 12              | 66 / 80                 | 4（孙桥小学校区）  |

孙桥小学在 2026 年招生公示中有张江、申江两个校区，招生地段只写到学校。两个校区到同一小区的距离可以相差 1 km 以上（川杨新苑三期：张江校区 310 m、申江校区 1,386 m），推定校区会直接改变结论，所以如实标为待核实，待向学校确认。

典型案例：

- 樟盛苑（玉兰香苑片区）：张江社区卫生服务中心直线 759 m，步行 1,390 m（绕路 1.83 倍）。
- 川杨新苑四期（申城佳苑片区）：浦商生鲜(申城佳苑店) 直线 734 m，步行 1,281 m。
- 日月光员工生活区：对口的张江镇中心小学直线 1,336 m、步行 1,362 m，直线也远。

## 13. 风险与对策

| 风险                       | 影响           | 对策                                                                                            |
| -------------------------- | -------------- | ----------------------------------------------------------------------------------------------- |
| 百度"住宅区"检索混入非住宅 | 凭空多出缺口   | 名称规则剔除居委会；人工核实清单（uid、理由、来源、日期）在实时体检中生效；新片区按同样流程核实 |
