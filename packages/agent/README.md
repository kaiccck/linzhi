# @zoudedao/agent · 体检顾问与工具注册表

走得到的 AI 层（技术设计文档 §8）：

- **一套工具注册表**，同时供体检顾问（OpenAI 兼容的工具调用）和 MCP Server（`@zoudedao/mcp`）使用。
- **数字溯源校验**：回答里的每个数字都必须来自本轮工具结果，并标注来源编号 `[T1]`；校验不通过就让模型修正一次，仍不通过就改用模板回答。
- **体检顾问**：配置大模型时由模型规划工具调用；不配置时由关键词路由调用同样的工具、用模板组织回答——评委不配置任何 Key 也能完整使用。
- **确定性的体检报告**：Markdown / GeoJSON / JSON，同一份分析结果总是生成同一份报告。

所有工具结果都只由分析结果（`AnalysisResult`）计算得出，不经过任何大模型，可以复现。

## 工具

| 工具                                                                                     | 返回                                                                                                                                                                                       |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `locate_place` `{query, city?}`                                                          | 候选中心点（BD-09）与 `needs_confirmation`                                                                                                                                                 |
| `analyze_life_circle` `{sample_id? \| analysis_id? \| center_bd09? \| place?, profile?}` | `analysis_id` 与核心数字（见下表），含圈内设施统计 `facilities` 与灰色区域 `gray_areas`                                                                                                    |
| `get_isochrone` `{analysis_id, levels?, crs?, simplify?, include_circle?}`               | 5/10/15 分钟等时圈 GeoJSON（MultiPolygon，保留孔洞）+ 直线 15 分钟圆 + 中心点                                                                                                              |
| `list_service_gaps` `{analysis_id, category?, status?, community?, include_pending?}`    | 已核实的缺口（按步行距离排序，含直线/步行距离、经由设施、步行分钟）；待核实单独列出；`by_community` 每个小区一行（各类设施的判定与步行分钟）；指定 `community` 时另附该小区能走到的设施    |
| `simulate_facility` `{analysis_id, category, center_bd09 \| near_community}`             | 新增设施后各小区的 L̂ 估算与变化；**恒为估算**                                                                                                                                              |
| `compare_sites` `{analysis_ids: 2–4 个}`                                                 | 并排指标与“最严重/最多”的结论（相同时如实说相同）                                                                                                                                          |
| `export_report` `{analysis_id, format}`                                                  | Markdown 报告（含“圈内设施”“灰色区域”两节）/ GeoJSON 地图数据（设施点带 `walk_min`、`within_walk15`、`within_circle15`，灰色区域带面积与涉及小区，集合带 `facility_stats`）/ JSON 报告模型 |

每个工具返回 `ToolResult { summary, data, facts, anchors? }`：`summary` 是给人看的中文摘要（结论先行），`data` 是结构化数据，`facts` 是摘要里每个数字的 `{ label, value, unit }`，`anchors` 是结果提到的地点（见下）。单元测试逐一验证：每个摘要里的数字都在它自己的 `facts` 中，`data` 都符合声明的 `outputSchema`。

**证据锚点**（`anchors.ts`）：让回答的来源编号能在地图上高亮对应的地方。四种：`community`（名称、Web 的地图编号 `code`、局部坐标 `xy`、BD-09）、`poi`（名称、uid、类别、位置）、`gray_area`（`gap-1` 这样的层编号、在 `gray_areas` 中的位置、面积）、`site`（模拟的新设施位置），每个都带 `analysis_id`。`analyze_life_circle` 给灰色区域各层、有已核实缺口的小区、各类最近的设施；`list_service_gaps` 给缺口小区与其步行能到的设施、待核实的小区；`simulate_facility` 给新位置与能补上的小区；其他工具不给。地图编号由 `communityCodes(result, id)` 按与 Web 相同的规则算出（由北向南、再由西向东，`A-01`…，字母取样例 id 末位）。锚点不交给大模型、不参与数字校验，每条最多 40 个；顾问把它们放在 `citations[].anchors`，服务端的 `POST /api/ask` 原样下发。

## 数字溯源校验

`checkGrounding(answer, sources)` 提取回答中所有阿拉伯数字（千分位、小数、百分数、单位、`5、10、15 分钟` 这样共用单位的列表和范围、日期、`GB 12345-2020` 这样的标准号），逐一在工具结果（`facts`、摘要、结构化数据）、用户自己的问题和少量领域常数中查找。

| 规则                                                                                         | 例子                                                                                                                    |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 原值、千分位、末尾零都可以                                                                   | 1,053 m = 1053 m；1.880 倍 = 1.88 倍                                                                                    |
| 单位换算：m↔km、m²↔km²、秒↔分钟↔小时、比例↔百分数                                            | 1,053 m → 1.053 km；0.533 → 53.3%                                                                                       |
| 四舍五入到 0–3 位小数，但必须保留至少 3 位有效数字（工具值本身不足 3 位时，与工具值相同）    | 1.857 km² → 1.86 km² 可以；**1.88 倍 → 1.9 倍或 2 倍不可以**；53.3% → 53% 不可以；1,053 m → 1.05 km 可以、1.1 km 不可以 |
| 带物理单位（m、km²、分钟、倍……）的数字只能匹配带同类单位的工具值；无单位的工具值只能支撑计数 | 数据里的 `straight_gaps: 2` 能支撑“2 个缺口”，不能支撑“2 倍”                                                            |
| 领域常数必须带单位                                                                           | 5/10/15 分钟、1,000 m、1 km、50 m、1.17 m/s、0.9 m/s（老年人步速）                                                      |
| 几何坐标、原始样本不作为来源                                                                 | GeoJSON 的坐标里有 121.1 也不能支撑回答里的 121.1                                                                       |
| 由工具结果支撑的数字，所在句子必须标注包含它的结果编号                                       | “画圆高估 1.88 倍 [T1]。”；表格可以在表前或表后统一标注；句号后紧跟的一个或几个编号属于前一句                           |

为什么 1.9 倍不算：四舍五入到更少的位数本身就是模型在做运算；而且一个编造的 1.9 恰好可以藏在真实的 1.88 后面。宁可让模型原样引用，也不接受“差不多”。

找不到出处的数字如果恰好是某个工具值的舍入（24 分钟 ← 23.9 分钟，1.7 公里 ← 1,676 m），`details[].near` 给出那个原值，修正提示据此请模型照抄；求差、求和或编造的数字没有这个提示，免得把模型引向一个不相关的值。

**引用补全**（`completeCitations`）：回答里的数字都有出处、只是所在句子没有标注或标错了来源编号时，在句末补上包含该数字的结果编号——“5 个是小学伪覆盖 [T2]。”→“5 个是小学伪覆盖 [T2][T1]。”。出处本身没有变（数字已经在那个结果里找到），读者只是得到模型漏写的指向，不必为此让模型重写一轮；表格和含有无出处数字的句子不补。

局限：校验证明的是**出处**，不是**含义**。小的计数在一次分析里反复出现（6 个小区能走到小学、6 个小学缺口），模型把一个真实的 6 用在错误的地方时，数值校验无法发现；引用校验会把范围缩小到被引用的那个工具结果。

## 体检顾问

```ts
import { createAdvisor, HttpBackend, LocalBackend, llmConfigFromEnv } from '@zoudedao/agent';

const advisor = createAdvisor({
  backend: process.env.ZDD_API_URL
    ? new HttpBackend(process.env.ZDD_API_URL)
    : new LocalBackend({ samplesDir: 'data/samples' }),
  llm: llmConfigFromEnv(), // 未配置 LLM_BASE_URL / LLM_MODEL 时为 null：模板模式
  maxSteps: 6,
});

const r = await advisor.ask('申城佳苑的老人买菜方便吗？', { analysisId: 'zj-a', onEvent: console.log });
// r.answer      中文回答，数字带 [T1] [T2] 来源
// r.mode        'llm' | 'template'
// r.citations   [{ id: 'T1', tool: 'analyze_life_circle', args, summary, facts, anchors }, …]
// r.grounding   { ok, unsupported, checked, uncited, details }
// r.citationsAdded 系统补全了来源编号的数字，如 ['5 个 → T1']（见“引用补全”）
// r.fallback    模型回答未通过校验、改用模板时的原因
// r.attachments export_report 生成的文件
```

**大模型模式**：系统提示词（`systemPrompt()`）逐条写明：数字原样来自本轮工具结果（不四舍五入、不换单位、不求差值比例、不自己数个数）；每句含数字的话、包括结论句都标注 `[T#]`；历史对话里的数字和编号只属于那一轮；工具没有的数据（评分、等级、排名、房价）不编造；待核实不是缺口，模拟结果写明估算；体检覆盖哪些设施（“看病”看社区卫生和药店）；已知 analysis_id 直接调用、同一轮并行调用；用户说的地点不在已有分析里就如实说明并指向搜索框，不拿当前分析冒充。回答首行“结论：”，最多 5 条要点。每条规则都对应真实模型出过的问题，见下文“真实模型评测”。

工具调用循环最多 `maxSteps` 轮。最终回答做数字溯源校验：数字都有出处、只是来源编号漏标或标错时，由系统补全编号（`citationsAdded`）；有找不到出处的数字时，把每个数字的问题和改法（照抄工具里的原值，或删掉）列给模型修正一次（`repairPrompt()`）；仍不通过就改用模板回答，并在 `fallback` 里说明原因。改写后的引用不比初稿好、而初稿数字都正确时，保留初稿。

**模板模式**：关键词路由决定调用哪些工具——买菜/菜场 → 菜市场，买药/药店 → 药店，上学/小学 → 小学，老人 → 老年人画像，“如果…开/新增/建” → 新增设施模拟，对比 → 社区对比，报告/导出 → 体检报告，“圈里有几家药店”“附近有什么设施”“附近有地铁吗”（问设施数量或社区卫生、养老、公交、地铁、公园、超市，不问小区）→ 圈内设施统计，地名 → 样例匹配或定位。回答由工具结果拼成，同样带 `[T#]` 来源，并同样通过数字溯源校验。例如：

```text
问：申城佳苑的老人买菜方便吗？
结论：不太方便：申城佳苑片区 12 个小区中，有 4 个步行 1,000 m 内走不到菜市场（伪覆盖 3、盲区 1）[T2]。

- 按老年人步速 0.9 m/s，15 分钟最多走 810 m，12 个小区里只有 3 个能在 15 分钟内走到菜市场 [T2]。
- 川杨新苑四期：到菜市场直线 1,084.1 m，实际步行 1,714 m，约 31.7 分钟（盲区）[T2]。
- ……
```

```text
问：申城佳苑圈里有几家药店？
结论：申城佳苑片区：15 分钟步行能走到药店 8 家（直线 15 分钟圆内 9 家，清单共 11 家），最近的是医保药店(高木桥路店)，步行约 2.7 分钟 [T1]。

- 直线 15 分钟圆（半径 1,053 m）里的设施，步行 15 分钟不一定走得到：河道、高架和封闭小区会让路绕远 [T1]。
```

事件：`tool_call`、`tool_result`、`progress`（实时体检的阶段）、`repair`、`fallback`、`answer`。

## 真实模型评测

评测集 `test/fixtures/llm-eval/cases.json`：20 个街道规划人员和评委会问的问题，覆盖 4 个张江样例（zj-a 申城佳苑、zj-b 玉兰香苑、zj-c 万科翡翠公园、zj-v AI小镇服务中心周边）：买菜、上学、药店、老人、对比、假如新增、导出报告、附近设施、超出范围的地名（“陆家嘴怎么样？”“帮我看看徐家汇那边老人看病方便吗”）、带历史的追问，以及两道陷阱题（“老人和成人比，范围小了多少”诱导求差，“能打几分”诱导自创评分）。每题自动检查：数字核验（有出处、有引用）、是否需要修正、是否回退模板、首行是否“结论：”、要点是否不超过 6 条，以及题目自己的要求（估算必须写“估算”，超出范围必须如实说明并指向搜索框，导出必须有文件，评分题必须说明没有评分）。

```bash
pnpm --filter "@zoudedao/agent..." build          # 脚本运行构建后的包（Node ≥ 22.18 直接运行 .ts）
cd packages/agent
node --env-file=../../.env.local scripts/eval-llm.ts                  # 本进程：与 POST /api/ask 相同的顾问和数据，只用样例，不调用百度接口
node --env-file=../../.env.local scripts/eval-llm.ts --record         # 同时重写录制文件 test/fixtures/llm-eval/recorded.json
node scripts/eval-llm.ts --api http://localhost:8787 --out 结果.json  # 经运行中的服务，与 Web 完全相同的路径（遇到限流自动等待）
node scripts/eval-llm.ts --report 结果.json                           # 不调用模型，按当前的检查重新评分
```

Key 只从环境变量读取，不会被打印或写进结果；`--only q01,q07` 只跑部分题目（与 `--record` 合用时只替换这几题的录制），`--max-calls` 限制模型调用次数。

| 问一个小区时，把片区级“15 分钟内能走到小学的小区 6 / 12”读成“6 所小学（共 12 所）” | `list_service_gaps` 指定 `community` 时不再返回片区级 `within_15min`：这是数字校验发现不了的“真实数字用错地方” |
| 问“哪些小区都方便”，工具只给缺口清单，叫不出方便的小区                             | `list_service_gaps` 增加 `by_community`：每个小区一行，各类设施的判定与步行分钟                                |
| 每题 2–3 轮工具调用                                                                | 提示词：已知 analysis_id 直接调用、同一轮并行调用；老年人画像直接用 `<id>~elder`                               |

模板模式（大模型不可用时的回退）也修了三处：地名里带设施词（“万科翡翠公园片区买菜方便吗”不再被当成问公园）、片区名里包含同名小区（“万科翡翠公园片区”不再被当成小区“万科翡翠公园”）、连用的客套前缀（“帮我看看徐家汇…”的地名是“徐家汇”）。

### 离线回放

`test/llm-eval.test.ts` 用录制的模型原始响应代替模型、用录制的工具结果代替工具，把 20 题重新走一遍：工具调用、回答、修正与核验结果都必须和录制时一致，并断言评测目标（一次通过 ≥ 90%、没有回退、首行结论、要点不超过 6 条、各题要求全部满足）。改动 `grounding.ts` 或顾问循环时，如果会拒绝（或放过）某个真实模型的回答，这里不联网就能发现。录制文件不含任何 Key；每题记录了当时提示词（系统提示词、修正提示、工具定义）的指纹，提示词改动后测试会提示重新录制。

## 大模型配置

任何兼容 OpenAI Chat Completions（`POST {LLM_BASE_URL}/chat/completions`，支持 `tools`）的服务都可以。

| 环境变量         | 说明                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------- |
| `LLM_BASE_URL`   | 接口地址（不含 `/chat/completions`）                                                      |
| `LLM_API_KEY`    | API Key，只放在 `Authorization: Bearer` 请求头里，不写日志；错误信息里出现的 Key 会被打码 |
| `LLM_MODEL`      | 模型名                                                                                    |
| `LLM_EXTRA_BODY` | 可选，合并进每次请求体的 JSON，例如 `{"enable_thinking": false}`                          |
| `LLM_TIMEOUT_MS` | 可选，单次请求超时，默认 60000                                                            |

### 常用服务的配置（2026-09-27 按官方文档核对）

| 服务                   | `LLM_BASE_URL`                                      | `LLM_MODEL`（支持工具调用）              | 建议的 `LLM_EXTRA_BODY`            | 说明                                                                                                         |
| ---------------------- | --------------------------------------------------- | ---------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 百度千帆（文心 ERNIE） | `https://qianfan.baidubce.com/v2`                   | `ernie-5.1`（或 `ernie-5.0`）            | 不需要：`enable_thinking` 默认关闭 | Key 为千帆控制台创建的 API Key（形如 `bce-v3/ALTAK-…`）；`tool_choice` 支持 `auto`/`none`                    |
| DeepSeek               | `https://api.deepseek.com`                          | `deepseek-flash`（或 `deepseek-v4-pro`） | `{"thinking":{"type":"disabled"}}` | `deepseek-chat`、`deepseek-reasoner` 已于 2026-07-24 下线；新模型默认开启思考                                |
| 通义千问（阿里云百炼） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus`（或 `qwen3-max`）            | `{"enable_thinking": false}`       | Key 与接入地域须一致；开源 Qwen3 在思考模式下只支持流式调用；`tool_choice` 不支持 `required`（本项目不使用） |

```bash
# 例：百度千帆
export LLM_BASE_URL=https://qianfan.baidubce.com/v2
export LLM_API_KEY=<千帆控制台创建的 API Key>
export LLM_MODEL=ernie-5.1
node packages/agent/dist/cli.js "申城佳苑的老人买菜方便吗？"
```

几点说明：

- 模板模式是默认值，不配置任何变量也能完整使用；配置后大模型只负责规划工具调用和组织语言，数字仍然全部来自工具。
- 客户端只使用非流式调用、`tool_choice` 的 `auto` 和 `none`，这是三家都支持的交集。
- 思考模型在工具调用循环里要求把上一轮的 `reasoning_content` 原样带回（DeepSeek V4、ERNIE 5 的交错思考）；客户端会自动带回，只在服务返回了它时才发送。关闭思考仍然是更快、更省的选择。
- 阿里云百炼推荐新的接入地址 `https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`，旧域名 `dashscope.aliyuncs.com` 自 2026-09-30 起不再支持新特性，但仍可调用；国际站为 `https://dashscope-intl.aliyuncs.com/compatible-mode/v1`。
- 模型更新很快，以上型号请以各家官方文档为准：[千帆 OpenAI 兼容接口](https://cloud.baidu.com/doc/qianfan-api/s/3m7of64lb)、[千帆函数调用](https://cloud.baidu.com/doc/qianfan-docs/s/xm95lyys5)、[千帆模型列表](https://cloud.baidu.com/doc/qianfan/s/rmh4stp0j)；[DeepSeek API 文档](https://api-docs.deepseek.com/)、[思考模式](https://api-docs.deepseek.com/guides/thinking_mode)、[工具调用](https://api-docs.deepseek.com/guides/tool_calls)；[百炼 OpenAI 兼容](https://help.aliyun.com/zh/model-studio/compatibility-of-openai-with-dashscope)、[通义千问函数调用](https://help.aliyun.com/zh/model-studio/qwen-function-calling)、[深度思考](https://help.aliyun.com/zh/model-studio/deep-thinking)。

## 数据来源（后端）

| 类                             | 说明                                                                                                                                                                                                             |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HttpBackend(baseUrl)`         | 走得到服务（`docs/api.md`）：`/api/samples`、`/api/analysis/:id`、`/api/locate`、`POST /api/analyze`（解析 SSE 的 `stage`/`partial`/`quota`/`result`/`error` 事件）。样例模式下的 409 转成中文说明；有超时和取消 |
| `LocalBackend({ samplesDir })` | 直接读 `data/samples/*.json`；定位只匹配样例名称、中心点标注和样例里的小区；不能实时分析                                                                                                                         |
| `AnalysisStore`                | 内存中的分析结果（最近 16 个）。实时结果的 id 为 `live-<8 位哈希>`，老年人画像为 `<id>~elder`（按需由原结果换算）                                                                                                |

## 模块

| 文件                      | 内容                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------- |
| `analysis.ts`             | 核心推导：“画圆 vs 步行”缺口对比、分类计数、老年人画像换算、L̂ 估计器                              |
| `summary.ts`              | 概览与结论句（工具、报告、模板顾问共用）                                                          |
| `geo.ts`                  | 局部坐标 → BD-09（按 `meta.frame_formula`）→ WGS84 / GCJ-02，GeoJSON                              |
| `anchors.ts`              | 证据锚点（小区、设施、灰色区域、模拟位置）与 Web 地图编号 `communityCodes()`                      |
| `report.ts`               | 体检报告模型与 Markdown                                                                           |
| `grounding.ts`            | 数字提取与溯源校验                                                                                |
| `llm.ts`                  | OpenAI 兼容客户端（fetch，工具调用，超时，5xx 重试一次，思考模型的 `reasoning_content` 自动带回） |
| `advisor.ts`、`intent.ts` | 体检顾问与模板模式的关键词路由                                                                    |
| `tools/`                  | 七个工具与注册表（zod 输入模式，`toOpenAITools()` 导出 JSON Schema）                              |
| `scripts/`                | 真实模型评测：`eval-llm.ts`（运行、录制、重新评分）与 `eval-lib.ts`（检查与指标，回放测试共用）   |
