# @zoudedao/eval

邻至的精度–配额评测（技术设计文档 §5.9、§11）：用稠密实测的参考网格做真值，回答“等时圈有多准，和用了多少条百度路线是什么关系”，并与两种常见做法对比。它产出“真实对比测试报告”的数据、表格和两张图。

评测只调用两种接口：批量算路（步行）和轻量步行路线。**不调用地点检索、逆地理编码、地理编码**（评测账本把它们的上限设为 0）。

## 方法

**参考真值**：以区域中心为原点，1,600 米圆内 100 米格点上的每一个点（不含中心，共 796 点），用批量算路从中心各测一条步行路线（1 × ≤ 50 条/请求；同一次运行内失败的格子重试 1 次；百度无路线的点记为 `no_route`）。耗时 = 路线距离 ÷ 1.17 米/秒（百度批量算路的步速）。结果冻结为 `reference.json`，带坐标（局部米制 XY 与 BD-09）、`route_m`、`dur_s`、状态和每次运行的调用记录。可续测：已测的点不再请求，每次调用后立即保存。

**对比的方法**（每个方法给出 15 分钟区域，有耗时场的给出耗时场，并记录自己的路线成本）：

| 编号                   | 方法                                                                                                                                          | 批量算路 | 步行路线 |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------- |
| `circle`               | 直线圆：半径 900 秒 × 1.17 米/秒 = 1,053 米；耗时按直线距离 ÷ 1.17 估计                                                                       | 0        | 0        |
| `star16`               | 16 方位射线法（常见做法）：16 个方位 × 347 / 705 / 1,053 米，沿每条射线对耗时线性插值，取首次达到 900 秒处；16 个可达点连成多边形；不给耗时场 | 48       | 0        |
| `seed48`               | 本方法只用这 48 条路线（不走步行路线、不加密）：同样的数据，只换估计方法（绕行系数 ρ 的去趋势插值）                                           | 48       | 0        |
| `engine@B`             | 实时引擎（只生成等时圈），批量算路共 B 条，用满预算不提前停止；B = 48、100、200、400、700                                                     | B        | 4        |
| `engine-default`       | 实时引擎的默认配置（个人档：粗采样 48 + 最多 4 轮 × 48），15 分钟区域两轮之间变化 < 3% 即停                                                   | ≤ 240    | 4        |
| `engine@700-nobarrier` | 消融：与 engine@700 同样的预算，关闭 Lipschitz 断裂检测                                                                                       | 700      | 4        |

几点设计：

- **16 方位射线法的 48 个点就是引擎粗采样的 48 个点**（坐标逐位相同），所以 `star16` 与 `seed48` 是“同样 48 条路线、两种算法”的直接对比，而且这 48 条只计费一次。
- **引擎的预算按“请求的路线”计数，命中缓存也算**（引擎选项 `budgetBasis: 'requested'`）。engine@B 无论缓存冷热，用到的样本都不超过 B 条路线，结果与冷启动完全相同；默认的“按计费计数”会让热缓存下的运行比冷启动多加密。
- **引擎只生成等时圈**（`scope: 'isochrone'`：不检索设施、不做盲区与选址），与完整体检的等时圈逐位相同（引擎测试覆盖）。
- **engine@B 按预算从小到大运行**：同样的样本 → 同样的加密点，所以 engine@200 的前几轮就是 engine@100 的全部请求，由缓存回答；每个预算只为多出来的轮次付费。默认配置的轮次是 engine@400 的前缀，不再计费。

## 指标

- **区域指标**（在 20 米网格、±1,600 米的节点上比较；参考区域 = 用同一套 `buildIsochrone`（去趋势插值 + 断裂可见性过滤）由参考点生成的耗时场中 < 900 秒的节点）：IoU、对称差面积、面积比，以及多算（方法有、参考没有）和漏算面积。
- **逐点指标**（直接用实测的参考点，不经过参考场的插值，避免参考自己的插值“帮”任何方法）：只取直线 ≤ 1,053 米（更远的点 15 分钟一定走不到，每个方法都会判对）且有实测结果的点，并去掉方法自己测过的点（5 米以内）。
  - 分类准确率：“15 分钟能否走到”判对的比例；边界带准确率只看参考耗时在 900 ± 180 秒之间的点。
  - 误判为可达 = FP ÷ (TP + FP)：方法说能到、实际到不了；误判为不可达 = FN ÷ (TP + FN)：实际能到、方法说到不了。
  - 耗时误差（有耗时场的方法）：|t̂ − t| 的平均值（MAE）、90 分位数，以及 t̂ − t 的平均值（负数 = 方法偏乐观）。引擎耗时场用双线性插值取值。
- **成本**：方法请求的批量算路条数（命中缓存也计数，即方法本身的代价）、生成时实际计费的条数、HTTP 请求数、步行路线次数、用时。
- 另报告参考场自身的留一法误差（区域指标受它影响，逐点指标不受）。

## 运行

在仓库根目录执行。`plan` 和 `score` 不需要 Key，也不联网；`run` 用 `eval:live`，它读取仓库根目录的 `.env.local`（`BAIDU_MATRIX_AK`、`BAIDU_SERVER_AK` 等，见 `.env.example`），缓存与配额账本与服务端共用 `BAIDU_CACHE_PATH`（默认 `data/cache/baidu.sqlite`），所以之前实时分析测过的路线直接命中缓存。

```sh
# 1. 看计划：每一步请求多少条、预计计费多少条（只读本地产物文件）
pnpm --filter @zoudedao/eval eval plan A
pnpm --filter @zoudedao/eval eval plan V --json

# 2. 执行（默认上限 = 计划的预计计费量；可以分步、分天跑）
pnpm --filter @zoudedao/eval eval:live run A --max-routes 2148 --max-walks 6
pnpm --filter @zoudedao/eval eval:live run V --steps reference --max-routes 796

# 3. 只用产物文件重算指标和图（不联网）
pnpm --filter @zoudedao/eval eval score A
```

参数：`--steps reference,star16,engine`（默认全部）、`--budgets 48,100,200,400,700`、`--spacing 100`、`--radius 1600`、`--dir <产物根目录>`（默认 `research/eval`）、`--redo`（重算已有的方法产物；参考网格从不重测）。区域：`A` 申城佳苑片区（121.644195, 31.19007）、`V` AI 小镇服务中心（海科路 1650 号，121.624269, 31.19307）、`B` 玉兰香苑片区、`C` 万科翡翠公园片区。

**硬上限**：`--max-routes`（批量算路条数）和 `--max-walks`（轻量步行路线次数）是本次运行本进程最多计费的量。账本在请求发出之前检查：下一个请求会超过上限就不发，运行干净地停止（退出码 3），已测的结果都已保存。命中缓存不计费，也不受上限约束。当日的 90% 软上限照常生效。提高上限后重跑同一命令即可继续：参考网格只测未测的点，已完成的方法跳过，中断的方法重跑时前面的请求全部命中缓存。

## 配额

`plan` 的输出（2026-09-28，产物目录为空时）。“路线”是各步请求的条数（含缓存命中）；“预计计费”是冷缓存下的上限——只会更少：之前的实时分析已经测过的粗采样和前几轮加密点、恰好落在参考格点上的加密点都由缓存回答。

| 步骤                 | 调用 | 路线（含缓存） | 预计计费路线 | 步行路线     |
| -------------------- | ---- | -------------- | ------------ | ------------ |
| reference            | 16   | 796            | 796          | 0            |
| star16               | 1    | 48             | 48           | 0            |
| seed48               | 1    | 48             | 0            | 0            |
| engine@48            | 1    | 48             | 0            | 4（≤ 6）     |
| engine@100           | 3    | 100            | 52           | 0            |
| engine@200           | 5    | 200            | 100          | 0            |
| engine@400           | 9    | 400            | 200          | 0            |
| engine@700           | 15   | 700            | 300          | 0            |
| engine-default       | 5    | ≤ 240          | 0            | 0            |
| engine@700-nobarrier | 15   | 700            | 652          | 0            |
| **合计（每个区域）** |      | **3,280**      | **≤ 2,148**  | **4（≤ 6）** |

- A 与 V 的计划相同：两个区域合计预计计费 ≤ 4,296 条批量算路（个人档每日 5,000 条，90% 软上限 4,500 条），建议分两天跑，或先跑两个区域的参考网格（各 796 条）。
- 消融（无断裂检测）按全部新增估计上限；合成城市里它的加密点与有断裂检测时大量重合，实际只计费 62 条。
- 参考网格的规模由 `--radius` 决定：1,600 米 796 点；1,300 米 528 点；1,200 米 440 点；1,100 米 376 点。15 分钟区域不会超出 1,053 米，逐点指标也只用 1,053 米以内的点，所以 `--radius 1200` 每个区域可省 356 条，代价是参考场在 1,200 米外只能外推（不影响 15 分钟区域）。
- 地点检索、逆地理编码、地理编码、坐标转换：0 次。

## 产物（`research/eval/<区域>/`）

| 文件                  | 内容                                                                                     |
| --------------------- | ---------------------------------------------------------------------------------------- |
| `reference.json`      | 参考网格：每个点的 XY、BD-09、route_m、dur_s、状态；每次运行的调用、计费、重试记录       |
| `methods/<方法>.json` | 方法的 15 分钟区域（闭合环）、耗时场（引擎）、自己测过的点、成本、引擎的加密轮数等       |
| `results.json`        | 全部指标（`score` 生成）                                                                 |
| `results.md`          | 中文表格：结论速览、区域对比、逐点检验、调用成本、参考真值、方法说明、指标定义           |
| `accuracy-quota.svg`  | 精度–配额曲线：IoU 与耗时 MAE 随批量算路条数的变化（两个小图共用横轴）                   |
| `overlay.svg`         | 参考 15 分钟区域（黄色）与 engine@400（钴蓝）、16 方位射线法（红）、直线圆（黑虚线）叠加 |

## 测试

```sh
pnpm --filter @zoudedao/eval test        # 34 个用例，约 8 秒，不联网、不读 .env.local
pnpm --filter @zoudedao/eval typecheck
pnpm --filter @zoudedao/eval build
```

测试用引擎测试里的合成河道城市（`packages/engine/test/city.ts`：100 米街道网格，x = 450 米一条河，只有 y = −300 米一座桥）和它的百度报文假传输（`packages/engine/test/transport.ts`），接在真实的 `BaiduClient` 上，所以分批、缓存、账本和评测上限都真实运行。覆盖：参考网格覆盖整个圆盘、在上限处停止后续测不重复请求、失败格子重试一次、两次失败的格子下次再测；16 方位射线法在河对岸多算、在近岸漏算，而大预算的引擎沿河给出正确边界、IoU 更高；手算的区域与逐点指标；上限取任何值都不会被突破（账本与报文两处核对），批量算路和步行路线超限都干净停止；`plan` 的请求条数与 `run` 实际请求的条数一致，计费不超过计划；第二次运行（空缓存）零请求；`score` 只凭产物文件得到同样的数字；命令行（`test/cli.test.ts`）按运维时的真实路径运行：没有 Key 时不碰缓存和网络（退出码 2），在 `--max-routes` 处停止（退出码 3）、不加参数重跑时按剩余计划的上限续完，SQLite 缓存与账本真实读写。

## 局限

- 参考真值本身也是百度批量算路（步行耗时 = 距离 ÷ 1.17 米/秒，不含红绿灯等待），评测的是“逼近稠密百度实测”的程度，不是与实地步行的比较（实地计时见技术设计文档 §11.2）。
- 区域指标依赖参考场的插值（100 米格点之间），所以同时报告逐点指标；参考场的留一法误差写在结果里。
- 方法测过的参考点不参与它自己的逐点检验，各方法的检验点数因此略有不同（表中注明去掉的点数）。
- 计划里的计费条数是上限；引擎加密点若提前用完（边界带没有可选的候选点），实际请求会少于 B。
- 用时包含限流等待，缓存命中时很短，只作参考。
